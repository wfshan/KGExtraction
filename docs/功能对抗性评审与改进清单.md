# 功能对抗性评审与改进清单

> 范围：文档上传（切片设置 / 导入类型 / 图谱数据导入）、Schema 配置、智能抽取、人工复核、图谱可视化、问图。
> 视角：作为「知识抽取 / 知识工程」产品，逐一审查设计合理性、实现一致性与可丰富空间。
> 优先级：**P0 = 正确性/一致性缺陷（会产出错误结果或误导用户）；P1 = 体验/能力短板（影响可用性与知识质量）；P2 = 增强项（锦上添花）。**
> 说明：本文件是「待更新」清单，用于确认后再落地修改，不代表已实现。

## 一、文档上传

### 切片设置

- **P0｜层次切片对 PDF/DOCX 失真，且重切时结构已丢失。** `chunker.py` 的 `hierarchical` 依赖 Markdown 标题正则识别层级，但 PDF/DOCX 在 `parser.py` 解析阶段已被拍平为纯文本，标题层级信息不复存在；`documents.py` 的 rechunk 仅对 `md` 重新读原文，PDF/DOCX 无法恢复结构。结果：对最需要结构的格式，"层次切片"退化为普通切分，却仍以"层次"名义呈现给用户。
  - 建议：解析阶段保留结构标记（DOCX 用 heading style、PDF 用字号/书签），或在 UI 明确标注"层次切片仅对 Markdown/带标题文本生效"，避免误配。

- **P1｜`start_char` 定位近似，逐字证据校验存在偏移风险。** 切片起始位置用 `text.find` 兜底，重复文本会命中错误位置。表面知识的"逐字证据校验"依赖 chunk 原文，偏移会导致证据命中判断出错。
  - 建议：切片时精确记录 offset（顺序消费指针而非全局 find），保证证据溯源可靠。

- **P2｜缺少切片预览。** 用户设置切片参数后无法在导入前看到切片效果（片数、每片长度分布、边界样例），只能抽取后才发现切得过碎或过长。
  - 建议：上传后提供"切片预览"（片数 + 前若干片文本），支持调整参数后重切。

### 导入类型支持

- **P0｜解析在请求线程内同步执行，大文件阻塞。** `documents.py` 的 `upload_document` 把文件全量读入内存并**同步解析**，仅向量索引走 BackgroundTask。大 PDF/大 xlsx 会长时间占用请求、前端等待甚至超时。
  - 建议：解析也转入后台任务，文档状态置 `parsing → parsed/failed`，前端轮询；同时加入文件大小上限与流式读取。

- **P1｜无内容去重。** 无 content-hash 去重，重复上传同一文件会产生重复片段与重复抽取，污染图谱且浪费 token。
  - 建议：按内容哈希识别重复，命中时提示"已存在，是否覆盖/跳过"。

- **P1｜表格类语义在纯文本化后丢失。** CSV/xlsx 被拍平为 `col | col`，DOCX 表格提取为文本；行列对应、表头与单元格的结构关系丢失，关系抽取难以还原"同一行的字段互为属性"。
  - 建议：对结构化文件走专门分道（已在 schema 分道有雏形），把"表头→字段"显式作为候选属性/关系喂给抽取，而非退化为自由文本。

- **P2｜格式覆盖有限。** 当前 `ALLOWED_EXTENSIONS = {pdf, txt, md, docx, csv, xlsx}`，缺 pptx、html、json 纯数据、图片 OCR 等常见知识源。
  - 建议：按需扩充；不支持的格式在上传前明确拦截并提示。

### 图谱数据导入（冷启动）

- **P0｜合并只按 name，与系统 (name, type) 身份不一致。** `graph.py` 的 `import_graph_data` 用 `existing_name_map = {n.name: n}` 合并，而抽取/写图全程用 `sha1(entity_type, name)` 作为身份。后果：同名不同类型实体被错误合并；导入后再抽取会因身份口径不同产生重复节点。
  - 建议：导入统一走 (name, entity_type) 身份与确定性 ID，复用抽取侧的 upsert 逻辑。

- **P0｜导入绕过治理：无 Schema 校验、无抽象度、无审计。** 导入直接写图，不校验类型是否在 Schema 内、不设 `abstractness`、不写审计日志，用 `source_chunk_ids=["cold_start"]` 哨兵。这些数据后续无法被发布门控、复核队列、缺口演化正确纳管——等于在"可治理"体系上开了个后门。
  - 建议：导入也过一遍 Schema 校验与门控预演；给导入节点默认 `abstractness=surface` 并记审计；`cold_start` 作为正式来源类型而非字符串哨兵。

## 二、Schema 配置

- **P0｜`update_schema` 无一致性校验。** `routers/schema.py` 的保存不校验关系的 source/target 类型是否存在于 `entity_types`。可保存"悬空关系"（指向不存在的实体类型），该关系在抽取时永远无法命中约束，静默失效。
  - 建议：保存时校验关系两端类型必须存在（或显式为"不限"），前端同步给出红色提示。

- **P1｜缓存失效不完整，会喂旧摘要。** `documents.py` 的 `_invalidate_schema_profile` 只删 `schema_profile.md`，但 `profiling.py` 同时缓存了 `schema_profile.json` 且优先读它。上传/删除文档后，Schema 建议与对话开场白仍基于**旧的 profile**。
  - 建议：失效时同时删除 `.json` 与 `.md`（两处路径已知）。

- **P1｜归纳类型的"结构模板"在 UI 缺位。** 设计中归纳类型带 `structure_template`（期望的结构化字段），Schema 建议已能输出，但 `SchemaEditor` 只暴露"抽象度下拉 + 定义 + 示例"，用户无法查看/编辑归纳知识应有的结构骨架。
  - 建议：归纳类型展开结构模板编辑区，与"归纳→结构校验 validate_structure"闭环对齐。

- **P2｜多入口易迷失。** Schema 页并列了「智能建议 / 对话配置 / 缺口演化 / 智能规划」四个 LLM 入口，语义相近（都在"帮我定 Schema/流程"），新用户难以判断先用哪个、彼此关系。
  - 建议：合并为一条引导式主线（先建议→再规划抽取语义→抽取后缺口演化），其余作为高级入口收起。

## 三、智能抽取

- **P0｜「查看抽取计划」文案与已实现能力矛盾。** `ExtractionRunner.tsx` 计划 Modal 仍写"当前为默认计划…**后续版本**将支持大模型按本体规划专用流程"，但"智能规划"在 Schema 页已经实现并能写回抽象度、编译出归纳分道步骤。文案自我否定，误导用户以为专用流程尚未上线。
  - 建议：更新文案为"计划由本体编译而来，可在 Schema 页『智能规划』调整各类型抽取语义"；并在计划里如实反映 inductive 分道步骤。

- **P0｜归纳知识置信度仍取 LLM 自报，未客观化。** 设计要求归纳知识可信度 = 支撑案例数（跨案例被反复归纳→更可信），但 `induction.py` 的 `induce_from_cases` 直接采用 LLM 返回的 confidence，且各分片独立归纳、无跨案例聚合（`merge_semantic` 仍在进行中）。后果：复核页对归纳知识展示的百分比置信度没有客观依据。
  - 建议：归纳分道以"支撑案例数"作为置信度来源，落地 `merge_semantic` 做跨案例同义归并与计数。

- **P1｜抽取目标（per-doc entities/relations）与抽象度分道解耦。** 目标配置只按实体/关系类型名勾选，未体现该类型是表面还是归纳；用户无法感知"勾了某归纳类型会额外触发归纳+忠实度校验（更贵更慢）"。
  - 建议：目标配置里标注抽象度徽标，并在成本预估中区分表面/归纳分道的调用量。

- **P2｜进度停滞判定较粗。** 3 分钟无更新即判"疑似中断"，长文档单片 LLM 调用可能正常超过该阈值，产生误报。
  - 建议：阈值与"单片预计耗时/剩余片数"挂钩，或由后端下发心跳。

## 四、人工复核

- **P0｜归纳知识被"逐字证据"话术误伤。** 复核队列证据列的红色"未验证"提示为"证据短句未能逐字命中原文"。归纳知识用 span 模式、`verified=None`，虽然 `has_verified_evidence` 视同通过（显示绿色），但一旦归纳项无 `evidence_quotes` 就落红，且话术只讲"逐字命中"，与归纳知识"靠忠实度校验把关"的机制不符，会让复核者误判。
  - 建议：证据列按抽象度分显示——表面："逐字已验证/未命中"；归纳："忠实度校验通过/待核"，两套话术分离。

- **P1｜置信度过滤对归纳知识不适用。** "仅显示低置信度 <80%"用统一百分比阈值，但归纳知识置信度语义应是支撑案例数。用一个百分比横切表面+归纳，会漏掉"仅 1 例支撑"的高风险归纳知识。
  - 建议：归纳知识按"支撑案例数"排序/过滤（如 <2 例重点复核），与表面知识分区呈现。

- **P1｜复核以扁平表格为主，缺"按来源/按争议聚类"。** 大图下逐行复核成本高，且无法一眼看出"哪个文档/哪类问题贡献了最多待复核项"。
  - 建议：复核队列支持按来源文档、按违规原因、按类型聚合，批量处置。

- **P2｜复核通过 ≠ 门控放行的提示已到位，但缺少"一键修正"。** 目前对违规项能提示"通过也会被过滤"，但用户仍需跳回 Schema 手动改类型。
  - 建议：违规项内联提供"改类型 / 加入 Schema / 拒绝"三选一的就地操作。

## 五、图谱可视化

- **P1｜cose 力导向布局在大图下不稳定且开销大。** `GraphPage` 增量更新后用节点数变化触发重跑 cose，节点数上千时布局抖动、卡顿；LOD 只调透明度/尺寸，未做真正的视口裁剪。
  - 建议：大图切换到更稳定的布局（fcose/concentric）或分层加载，默认强制探索模式并给出规模阈值提示。

- **P1｜归纳知识与表面实体在图上无视觉区分。** 概念/规则类归纳节点与人名/日期类表面节点同样着色（仅按 entity_type 配色），看不出"这是从案例概括出来的抽象知识"。
  - 建议：归纳节点用不同形状/边框/图标标识，详情面板显示"支撑案例"而非"来源片段"。

- **P2｜详情面板对归纳知识展示错位。** 面板固定展示"来源片段"，归纳知识的证据是"源案例摘录/结构模板"，套用片段视图信息含义不符。
  - 建议：按抽象度切换详情面板字段（表面=来源片段；归纳=支撑案例+结构字段）。

- **P2｜`cold_start` 哨兵在前端多处特判。** 详情面板、来源片段都在字符串比对 `'cold_start'`，脆弱且散落。
  - 建议：后端把来源建模为结构化字段（type: extracted/imported），前端按字段渲染。

## 六、问图（GraphRAG）

- **P0｜对话历史是项目级全局单文件，多会话/多用户互相污染。** `chat_store.py` 用 `chat_history.json` 单文件存整个项目的对话；`graph_rag.py` 的历史接口无任何会话/用户隔离。多人或多标签页同时问图会读写同一份历史。
  - 建议：按 session_id（或用户）分文件存储；接口带会话标识。

- **P0｜历史压缩拼接用了字面量 `"\\n"`。** `_compress_turns` 中 `messages_text = "\\n".join(...)` 是转义反斜杠，不是换行；压缩喂给 LLM 的多轮文本挤成一行，降低压缩摘要质量。
  - 建议：改为真正换行 `"\n".join(...)`。

- **P1｜检索模式过多（8 种）暴露给终端用户。** 独立流式/全向扩散/路径查找/关联检索/全局摘要… 概念门槛高，与产品"收敛用户交互入口"的方向相悖。
  - 建议：默认只给"智能路由"，其余收进"高级"；或由后端按问题类型自动选，弱化手动切换。

- **P1｜`global` 模式依赖社区摘要，auto 路由到它时可能空转。** 已有"构建社区摘要"入口提示，但 auto 模式下若路由到 global 而社区未构建，用户不一定看到该提示区（提示区仅在 mode 为 global/auto 时展示，尚可）。需确认 auto 实际路由到 global 时的降级策略。
  - 建议：auto 路由到 global 但无社区摘要时自动降级到其他模式并在召回详情注明，而非直接失败。

- **P2｜答案未强绑定"可溯源"。** 召回详情能看命中的实体/关系/片段，但答案正文里的结论未与具体证据条目建立可点击的引用锚。
  - 建议：答案中的关键结论标注 [来源#n]，点击定位到召回片段，强化"可治理/可溯源"卖点。

## 七、跨模块共性问题

- **P0｜抽象度（表面/归纳）贯穿链路存在断点。** 抽象度已在 Schema、抽取分道打通，但**导入**不设抽象度、**复核**用统一置信度话术、**可视化/详情**不区分归纳知识、**归纳置信度**未客观化。"归纳知识作为一等公民"这条主线在下游多处退化回"当普通实体处理"。
  - 建议：把"抽象度"作为端到端契约贯彻到导入、复核、可视化、置信度四处，作为一个成体系的改造项。

- **P1｜身份口径不统一。** 抽取用 `(type, name)` 确定性 ID，导入用 name，两者混用会造成重复与错配。应全局统一为一处 upsert 实现。

- **P1｜缓存/失效散落且不完备。** schema_profile 双文件缓存只失效其一；来源哨兵散落前后端。建议集中管理缓存 key 与失效点。

- **P2｜LLM 入口过多、心智负担重。** Schema 页 4 个 LLM 入口 + 问图 8 种模式 + 抽取多按钮，与"收敛用户交互入口"的产品定位有张力。建议做一次信息架构收敛，把"高级能力"分层收起。

## 建议的落地顺序

1. **先修 P0 正确性/一致性**（不改交互，风险最低）：导入身份与治理接入、schema 保存校验、profile 双缓存失效、`"\n"` 压缩 bug、抽取计划文案、解析异步化。
2. **再补抽象度端到端契约**（P0/P1）：导入抽象度、归纳置信度客观化 + `merge_semantic`、复核与可视化按抽象度分显示。
3. **最后做体验收敛与增强**（P1/P2）：入口收敛、切片预览、去重、大图布局、可溯源引用锚。
